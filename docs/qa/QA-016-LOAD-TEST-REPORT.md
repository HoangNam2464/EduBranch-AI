> **Master Task:** EBA-432 · **Sprint:** Sprint 4 — Learning & Review

## Result

**PASS WITH CONDITIONS for the tested local API workload.** The run completed the 50-Student steady-state profile with zero unexpected API errors and all authorization probes returned their expected status. This is an observation about this machine, local configuration and one Branching Study fixture; it is not an SLA or a guarantee for a production classroom.

LLM token and provider-cost measurement is **NOT AVAILABLE** in the inspected application telemetry. This profile made no AI/LLM calls, so no provider usage was generated by this run. No claim is made about cost or behavior for AI-backed endpoints.

## Authentication, RBAC and ownership evidence

All **22/22** negative authorization checks returned the expected status under the 50-VU stage:

- 5 missing-token requests → **401**.
- 5 Student attempts to list Lecturer-only Courses → **403**.
- 5 Student direct reads of a DRAFT Case → **403**.
- 5 Student attempts to call Case generation → **403**.
- 1 non-owner Lecturer direct Case read → **403**.
- 1 non-owner Lecturer Course Case list → **403**.

Student Case-list responses excluded the DRAFT Case. Student Case-detail responses did not expose nodes, options, consequences or next-node references. Successful Student flows read the completed Journey Review only after terminal completion. Lecturer owner requests remained successful concurrently with Student traffic.

No matching ERROR, exception, timeout or 429 lines were found in backend logs during the measured window.

| RustFS | 0.35% | 3.23% | 3.71% | 39.82 MiB |

Peak backend CPU can exceed 100% because Docker reports CPU across cores. The data suggests two areas to profile in a longer run:

1. **Concurrent authentication:** login p95 was 1.11 s and the maximum was 1.29 s. This was the highest observed endpoint latency; bcrypt work is a likely contributor, but this run did not isolate CPU time per function.
2. **Database-backed writes:** attempt creation and option selection had p95 around 182–210 ms while PostgreSQL CPU peaked at 51.98%. This is a candidate database/query/pool bottleneck, not a proven saturation point.

No agreed SLA, capacity threshold or production-sized hardware profile was supplied. The figures therefore describe observed behavior only.
